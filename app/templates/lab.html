Anatomy of Insecure Direct Object References (CWE-634)
Core Concept

An Insecure Direct Object Reference (IDOR) occurs when an application provides direct access to objects based on user-supplied input, but fails to perform sufficient server-side authorization checks to verify that the requesting user has permission to access that specific object.

Authentication vs. Authorization

Authentication confirms who you are (e.g. Alice logged in with valid credentials).

Authorization determines what you are permitted to do (e.g. Alice can view Document 101, but MUST NOT be allowed to view Bob's Document 201).

Common Developer Mistake: Verifying that a session exists, but assuming that any logged-in user can request any valid object ID.

The Myth of Obscure Identifiers

Replacing sequential IDs (e.g. 101) with opaque tokens or UUIDs (e.g. d3b07384d113...) makes guessing more difficult, but does not solve access control.

If an opaque identifier leaks (via referer headers, logs, or shared links), an unauthorized user can still access the data if the backend lacks ownership checks.

True access control requires server-side authorization on every protected request.

Exercise 3: Remediate Broken Authorization
Not Started

Objective: Understand how to implement server-side access control checks in application code and database queries.

Vulnerable Pattern (Omitted Ownership)

def get_document(doc_id): # Only verifies user is logged in user_id = session.get('user_id') if not user_id: return jsonify({'error': 'Auth required'}), 401 # FLAW: Queries ID alone without ownership check! doc = db.execute( "SELECT * FROM documents WHERE id = ?", (doc_id,) ).fetchone() return jsonify(doc) # Leaks other users' data!

Secure Pattern (Enforced Ownership)

def get_document(doc_id): user_id = session.get('user_id') if not user_id: return jsonify({'error': 'Auth required'}), 401 # FIX: Server binds query to authenticated session user! doc = db.execute( "SELECT * FROM documents WHERE id = ? AND owner_id = ?", (doc_id, user_id) ).fetchone() if not doc: return jsonify({'error': 'Forbidden'}), 403 return jsonify(doc)

Burp Suite Community Edition Manual Walkthrough
Tool Integration

Follow these steps to inspect and replay IDOR HTTP requests using PortSwigger Burp Suite Community Edition.

Step 1: Launch Burp Suite and Embedded Browser

Open Burp Suite Community Edition. Under the Proxy tab → Intercept sub-tab, click Open Browser. Navigate to http://localhost:5000.

Step 2: Log in as Alice and Intercept Document Request

Log in as alice. Open your dashboard or send a request for document 101. In Burp Suite, open Proxy → HTTP History and locate the request:

GET /api/documents/101 HTTP/1.1 Host: localhost:5000 Cookie: session=eyJfcGVybWFuZW50Ijp... Accept: application/json

Step 3: Send to Repeater and Replay with Bob's ID

Right-click the request in HTTP History and choose Send to Repeater (or press Ctrl + R).
In Repeater, change the URL path from /api/documents/101 to /api/documents/201.
Click Send.

# Vulnerable Mode Response: HTTP/1.1 200 OK Content-Type: application/json { "document": { "id": 201, "owner_name": "Bob Martin (Peer Reviewer)", "title": "Bob's Private Notes" } }

Step 4: Repeat in Secure Mode

Switch the lab to Secure Mode in the header. Re-send the same request for 201 in Repeater.

# Secure Mode Response: HTTP/1.1 403 FORBIDDEN Content-Type: application/json { "error": "Forbidden", "message": "Access denied: you do not have permission to view this document." }
